Audit Findings
5 Visual Inconsistencies to Mention

Each finding below includes a brief summary, what was found in the code, and a suggested talking point for the kickoff.

1
Buttons don't have a consistent hierarchy
Consistency

Six different button styling approaches exist across the codebase. Primary, secondary, and destructive actions don't consistently communicate their importance — each was styled independently on the page it first appeared.

.btn-yazaki main.scss:205
.button _buttons.scss:5
.button_approve _maindesign.scss:127
.button_new _maindesign.scss:147
.OpenRequestBtn main.scss:48
$btn-default-bg: #ffa31a custom-variables.scss:233
Current — 4 different button treatments on one screen
Submit Approve Default Open Request
After — Consistent 3-level hierarchy
Submit Approve Delete
What to say at kickoff

"One thing we noticed pretty quickly is that button treatments vary quite a bit across the application. As part of the refactor, we'd like to establish a more consistent primary, secondary, and destructive action hierarchy so users immediately understand what the main action is."

2
Color usage isn't consistently communicating meaning
Consistency

Status colors vary by page with no shared semantic pattern — red in some areas, orange in others. The audit also surfaced branding questions: Atlas blue (#264ae5) is the current interactive color but isn't a Yazaki brand color; there's an orphan teal (#559FAE, #2B6977) used in several places that has no defined brand role.

What to say at kickoff

"We also saw opportunities to tighten the color system — not necessarily changing the brand, but making sure color has a predictable meaning throughout the experience."

3
Visual hierarchy on complex screens could be clearer
Hierarchy

On Test Details, the three levels — Test Request → Test Leg → Spec Chapter — are mainly distinguished through indentation alone. Very little visual differentiation separates the levels. Users scanning a complex test record must read text labels to understand structure rather than perceiving it visually.

Current — indentation only, same visual weight at every level
TR Test Request TR26-7 — same font size, same card treatment as children
Leg Leg 1 — 26-7-1 — only indented, no visual container distinction
Ch 26-7-1-1 USCAR-2 REV 8 Failure Analysis — same visual level as parent leg
After — containers, accents, and type scale signal hierarchy
TR Test Request TR26-7 — bold section header, full-width
Leg Leg 1 — 26-7-1 — card container, red left border accent
Ch 26-7-1-1 USCAR-2 REV 8 Failure Analysis — lighter weight, clearly subordinate
What to say at kickoff

"On some of the denser screens, particularly Test Details, there's a lot of information competing at the same visual level. We'd like to explore using containers, section headers, spacing, and other subtle cues to make that hierarchy easier to scan."

4
Common components look different from page to page
Consistency

Similar functionality is presented differently depending on the page. Search is the clearest example — three different implementations exist across the application with no shared pattern, so users have to relearn filtering on each screen.

What to say at kickoff

"Another theme we saw is that similar functionality is sometimes presented differently depending on the page. Search and filtering are a good example. We want users to build familiarity instead of having to relearn the interface from screen to screen."

5
Page spacing and layout patterns aren't standardized
Standardization

The application contains several recurring page patterns — data grid pages, detail views, form pages — but they've been individually styled rather than built from shared templates. Data-grid pages in particular use multiple wrappers that style the same grid type differently, giving each screen an independently designed feel even though the underlying intent is the same.

What to say at kickoff

"A big opportunity for us is making repeated page types actually feel related — consistent headers, spacing, filters, grids, actions, and content regions instead of each screen feeling independently designed."

The Path Forward

Use this framing to pivot from audit findings into the design and build conversation.

Suggested transition at kickoff

"This isn't a redesign — it's standardization."

"So overall, we're not looking at this as a complete redesign. A lot of the underlying patterns are already there. What we want to do is identify the patterns that repeat, standardize them, and turn them into reusable page templates and building blocks. That should improve the visual consistency now and also make it easier for the Yazaki team to maintain that consistency as new pages are built."
