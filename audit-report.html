Audit Overview
Three Areas of Focus

The audit findings fall into three interconnected themes. Addressing them together — rather than screen by screen — is what makes the refactor sustainable.

🎨
Bucket 1
Consistency
Buttons, colors, spacing, page headers, and common components currently vary quite a bit depending on the screen.
📐
Bucket 2
Hierarchy
Some of the more information-heavy workflows could use clearer visual hierarchy so users can scan and understand relationships more quickly.
🔩
Bucket 3
Standardization
Rather than fixing those individually, the goal is to establish reusable patterns through the custom UI module, building blocks, and page templates.

Section 02
Major Recurring Page Patterns
Six distinct layout patterns identified across the application.
1 — Home / Launch Screen Medium Risk
Evidence: _home.scss · both modules
Fixed-padding tile grid with image backgrounds and hover-expand effect. Static 100px left/right padding hard-coded. No responsive grid wrapping. Hover-only descriptions are invisible to touch users.
2 — Request / Test List (Master-Detail) Critical
Evidence: _requestlist.scss · .RequestDataContainer
Left list panel (min 275px) + right detail panel fixed at min-width: 1400px. The detail panel contains a 76vh scroll container with both axes scrollable. Zero responsive collapse behavior defined.
3 — Test Details (Complex Hierarchy) Critical
Evidence: _maindesign.scss · .TestDetails-Container
Request → Test Legs → Spec Chapters → Resources/Schedules. Each level adds cumulative left margin (50px, 40px…). Nested scroll confirmed. EditSpecChapter-detail hard-coded at 920px wide.
4 — Data Grid Pages High Risk
Evidence: Custom-Datagrid.scss · .MyGrid2Style · .RQ-search
Full-width grid with sticky headers and pagination. Three different wrapper classes override the same grid differently. Grid forced to min-width: 91vw. No column-hiding strategy for tablet.
5 — Flyout / Right-Panel Drawer Medium Risk
Evidence: _flyoutpage.scss · _modal-slider.scss
Right-anchored 500–600px panel with slide animation. Two duplicate implementations. Panel hides its own title (h4 {display: none}). At 768px tablet the panel fills nearly the whole screen.
6 — Admin / Edit Spec Chapter Form High Risk
Evidence: _SpecChapterEdit.scss
Multi-column form with embedded data grid. Uses top: -50px positioning hacks to align sections. Fixed widths: 920px, 1300px, 400px. Entirely non-responsive.

Section 05
Top Responsive Risks
Ordered by severity — what will break most visibly at tablet widths.
Critical Risk 1 — .RequestDataContainer { min-width: 1400px }
Forces the entire detail panel to 1400px regardless of viewport. On a 1024px landscape tablet it overflows by 376px — creating page-level horizontal scrolling before any grid content is reached.
Critical Risk 2 — Nested Scroll Containers
.ScrollContainer has overflow-x/y auto at 76vh. Inside it, .widget-datagrid-content has overflow-y auto. Outer container scrolls, inner grid scrolls — disorienting and inaccessible on touch.
High Risk 3 — Tab Container Fixed Viewport Width
.tab-bordered { min-width: 93vw; max-width: 93vw } — at 768px portrait tablet this forces the content area to 714px, then content inside can still overflow that.
High Risk 4 — Cumulative Left Margins on Test Details Hierarchy
The tree uses stacking left margins (50px, 40px…) that work at desktop. At tablet widths, the starting container is narrower and the content pushes off-screen without any breakpoint adjustment.
Medium Risk 5 — Home Tile Wrapper Fixed Padding
.TileWrapper { padding-left: 100px; padding-right: 100px } — consumes 200px on an iPad mini portrait (768px), leaving only 568px for tiles expected to be ~300px wide each.
Medium Risk 6 — Flyout Panel at 600px on Tablet
At 768px portrait, the flyout's 600px width leaves only 168px of backdrop — effectively full-screen without acknowledging it. Should adapt to a smaller width or full-width bottom sheet on tablet.
Medium Risk 7 — Navigation at Mobile Breakpoints
No hamburger menu or collapsed navigation state is defined for mobile. The custom topbar overrides do not reference any responsive breakpoints, and the Atlas tablet layout file is not leveraged.
Medium Risk 8 — Fixed-Width Form Containers
EditSpecChapter-detail: 920px, AssignTestTypeContainer: 500px, Create-Edit: 350px — all fixed, none responsive.
Section 06
Top Usability Issues
Problems that affect how users accomplish tasks — independent of visual style.
U-1
Double horizontal scrolling on Test Details
Users scroll horizontally to see the full detail panel, then scroll horizontally again inside the embedded data grid. The single highest-priority fix.
Critical
U-2
No visual hierarchy between Request / Test Leg / Spec Chapter levels
Only left-margin indentation communicates hierarchy. No containers, lines, or color cues distinguish levels. LegContainer is rgb(216,216,216); BatchSupervisorContainer is rgb(245,245,245) — similar enough to be meaningless.
Critical
U-3
Button intent is ambiguous — no primary action hierarchy
The global .btn override makes every button a ghost. Primary actions are not visually distinct from secondary or destructive. Six competing button patterns exist with no semantic roles.
Critical
U-4
Status and state indicators have no shared vocabulary
Tab badges use Yazaki Red. UserRole text uses orange. Status fields use neither. No application-wide "approved = green / pending = amber / rejected = red" badge pattern.
High
U-5
Flyout panel hides its own title
h4 { display: none } — when a flyout opens, there is no visible heading. Users have no quick reference for what record they are viewing.
High
U-6
Home tile descriptions invisible on touch devices
.TileDescription { opacity: 0 } until hover. On tablet, hover does not fire reliably. Tile descriptions are effectively hidden from touch users.
Medium
U-7
Search placement is inconsistent across pages
.SearchContainerCollapse / Expand — some pages collapse search behind a toggle. Others show it inline. Others use the built-in grid filter row. Users must discover where search is on each page.
Medium
U-8
Empty states are not designed
No empty state component exists. When a data grid or list view returns no results, the default Mendix plain text message renders with no visual cue, icon, or guidance.
Medium

Visual Consistency Issues
Problems that undermine the appearance of a coherent design system.
VC-1 — Six Competing Button Systems Critical
.btn-yazaki .button .button_approve .button_new .OpenRequestBtn .btn-default (MyGrid2Style)
None defined in the Atlas variable layer. Shapes, colors, weights, and sizes vary page by page.
VC-2 — Orphan Teal Color Used in 6+ Places Critical
#2B6977
#559FAE
#559EAD
Teal is not a defined brand color in custom-variables.scss. Used in btn-yazaki, App-Button, Sequence-Label, home decoration — a leftover from an earlier design phase.
VC-3 — $LabelColor Not in Variable System High
Defined locally in _maindesign.scss as $LabelColor: #2B6977. Any other file needing the same color must re-define it or hardcode it. Not propagated through the theme.
VC-4 — White Topbar vs. Dark Navy Sidebar High
The custom topbar override sets background: white and red bottom border. The sidebar retains #020557. Two competing surface treatments make navigation feel split across two products.
VC-5 — Card/Surface System Is Inconsistent High
Four different card treatments in use simultaneously:
  • TestDetailsLegBox — modern box-shadow card
  • TileContainer — border: 2px solid darkred
  • EditSpecChapter-New — gray fill, no border
  • LegContainer — different gray fill, no border
VC-6 — Four Border Radius Conventions Medium
$border-radius-default: 4px is defined but ignored:
  • Buttons (.btn-yazaki): 20px pill
  • Tiles: 2% (relative!)
  • Cards (TestDetailsLegBox): 8px
  • Sequence labels: 20% (relative!)
VC-7 — Font Sizes Enforced via !important Medium
$font-size-default: 14px defined at top level. But .EditSpecChapter, .account-container, .role-container all override with font-size: 12px !important. The use of !important indicates the cascade is not being managed correctly.
Section 08
Data Grid Design Problems
Custom-Datagrid.scss is a strong foundation — the problems are in how it is applied and overridden.
💡
Note: The canonical Custom-Datagrid.scss should be preserved and extended, not replaced. The problems below are all in wrapper overrides and missing standardization — not in the core grid file itself.
1
Three Conflicting Grid Wrapper Classes
.MyGrid2Style, .RQ-search, .GridContainer all override the same .btn and .pagination-bar rules inside the grid. A single .dg-wrapper building block class should replace all three.
2
Grid Forced to 91vw — Not Responsive
max-width: 91vw; min-width: 91vw on the table. At 768px tablet that is 699px — works only if content fits, but many pages have 10+ columns. A responsive column-hiding strategy must be defined per page type.
3
No Standard for Column Priority at Tablet Width
No documented or SCSS-enforced pattern for hiding columns at smaller widths. Must be defined per page type: e.g., request list always shows Name + Status; hides Date Created + Assigned User at ≤768px.
4
Row Action Buttons Not Standardized
Row-level actions (Edit, Delete, Open) use the global .btn override. Some pages further override to 12px gray. A standard row-action button size and placement — rightmost column, icon-only at narrow widths — is needed.
5
Empty State Not Designed
Default Mendix plain text empty message renders with no icon, visual cue, or call to action. An empty state building block should be applied to every grid and list view.
6
No Decision: Filter Row vs. External Toolbar
Some grids use the built-in Data Grid 2 filter row. Others use external filter inputs above the grid. Both exist in the same application. Standard: prefer external toolbar for complex multi-field filters; use inline row filter for simple single-column filtering only.
7
Pagination Styling Conflicts Directly Override Canonical File
.GridContainer overrides pagination buttons to white. .EditSpecChapter-Resource-Grid forces pagination color to #ed1c24 !important at font-size: 5px !important. Both must be removed.
8
Column Header Font Weight Inconsistency
Custom-Datagrid.scss: font-weight: 600. _maindesign.scss: overrides to bold. _NewDesign.scss: overrides to normal, 12px. Three files override the same property three different ways.
Section 09
Information Needed From Client
These questions must be answered before representative screen designs can be finalized.
Users & Roles
  • Which user role should be used as the primary design reference? The SCSS references a "phone" role — .ApproveReject-Container_Phone, .button_menu_phone — suggesting at least two distinct UX paths.
  • Do phone/mobile users perform the same tasks as desktop users, or a subset?
  • How experienced are users with the current application? Affects how much we can change familiar patterns.
Test Details Page
  • What is the maximum number of Test Legs a single request typically has?
  • Can a user collapse/hide Test Legs they are not currently working on? .TestLegContainerExpand / Collapse classes exist — is this behavior already in place?
  • Is the horizontal scroll inside the Spec Chapter grid intentional? I.e., do users need all columns visible simultaneously?
Devices & Breakpoints
  • What tablet models are used in production? iPad, iPad Pro, Surface Pro, or other — affects breakpoint targets.
  • Is portrait or landscape the primary tablet orientation?
  • Are there shared-kiosk or wall-mounted display scenarios?
Branding
  • Is there an official Yazaki digital brand guide? Currently the primary UI color is Atlas blue (#264ae5), not Yazaki Red. Should the refactor correct this?
  • Should the topbar stay white (current) or return to dark navy to match the sidebar?
  • Should the orphan teal (#2B6977) be removed, or is it a sanctioned brand color?
Flyout / Admin
  • What is the flyout panel used for? Quick view, editing, or task assignment? The intent determines whether it stays a drawer or becomes a full modal.
  • Are Admin Center pages accessed by the same users as the main portal, or a separate admin team?
  • Are there bulk-action workflows in admin pages? Multi-select + batch operations change the grid design significantly.
Accessibility
  • Are there formal WCAG requirements?
  • Are keyboard navigation workflows expected by any user group?
Section 10
Three Design Directions
No screens have been designed yet. Select one direction — or a hybrid — to begin Phase 2.
⚠️
A hybrid is valid — for example, Direction B's visual approach delivered through Direction C's system-first method. If that is the preference, indicate which visual characteristics from B to prioritize.
A
Direction A
Conservative Refactor
Keep the existing visual language. Clean it up, enforce the variable system, fix responsiveness. Users will recognize the app — they'll just find it more consistent.
Key Visual Characteristics
White topbar, red bottom border — kept as-is
Dark navy sidebar — kept as-is
Primary button: Atlas blue (#264ae5) filled
Cards: subtle box-shadow, white, 6px radius
Open Sans unchanged, heading hierarchy tightened
Data grid headers: 600 weight, #f8f8f8 bg — consistent
Advantages & Tradeoffs
  • Lowest risk, no learning curve
  • Fastest to implement
  • Clean base for team to maintain
  • Least visible modernization
  • White/navy split unresolved
  • Still requires hard cleanup decisions
Implementation effort:
Low — primarily SCSS cleanup + building blocks
B
Direction B
Modern Enterprise
Clearly modernized appearance while keeping all workflows. The application should feel like a current enterprise tool, not a 2018-era portal.
Key Visual Characteristics
Full-width dark navy topbar — unified with sidebar
Page background: #f4f5f7 off-white
Cards: white, box-shadow, 8px radius
Primary button: blue (#264ae5), softened pill (6px radius)
Yazaki Red: accent only — tabs, badges, active states
Status badges: defined semantic palette (green/amber/red/gray)
Advantages & Tradeoffs
  • Visible, clear improvement
  • Enterprise-appropriate for manufacturing
  • Resolves split-personality navigation
  • Surface hierarchy solves most VC issues
  • More implementation work
  • Topbar change noticed by users
  • Needs full button system docs
Implementation effort:
Medium — layout files + full SCSS refactor
C
Direction C
Systemized Mendix UI
Eliminate every one-off style. Replace with a documented, reusable system of Building Blocks, Page Templates, variables, and design properties the team can maintain indefinitely.
Key Visual Characteristics
Close to Atlas UI defaults — known to Mendix developers
All decisions made through SCSS variables only — zero hardcoded values
Building blocks enforce consistency structurally
One and only one grid wrapper class — used everywhere
Five page templates — no new page built from scratch
Advantages & Tradeoffs
  • Highest long-term maintainability
  • Easiest for client team post-engagement
  • Most comprehensive documentation
  • Future changes = variable edits only
  • Least dramatic visual change
  • BB + template creation time-intensive
  • Some pages rebuilt, not just restyled
Implementation effort:
High up front — full system + client enablement guide
